# Сравнительный анализ: Одиночка vs Внедрение зависимостей

## 1. Когда одиночка может быть оправдан

**Одиночка оправдан в следующих случаях:**

- **Управление уникальными ресурсами**: подключение к базе данных, пулы соединений, логирование в файл (где действительно нужна одна точка синхронизации).
- **Глобальное состояние инфраструктуры**: обработчик исключений, счётчики метрик, работа с системными часами (если изменение часов должно быть видно везде).
- **Инициализация дорогостоящих операций**: компиляция регулярных выражений, загрузка больших словарей в памяти один раз.

**В нашем проекте:** конфигурация и аудит НЕ требуют одиночки. Это просто хранилища данных, которые должны быть подменяемы в тестах и управляемы контейнером.

## 2. Какие риски создаёт одиночка

### 2.1 Глобальное состояние

**Проблема:** любой код может обратиться к одиночке и неявно от него зависит. Сигнатура функции не показывает эту зависимость.

```python
def process_request(request_id):
    config = ConfigurationSingleton.get_instance()  # Скрытая зависимость!
    auditor = AuditorSingleton.get_instance()       # Ещё одна скрытая зависимость!
    # ...
```

**Тест такого кода:** необходимо вычищать состояние одиночек перед каждым тестом, иначе состояние утечёт из одного теста в другой.

### 2.2 Утечка состояния между тестами

**Проблема:** если забыть вызвать `reset()` в `tearDown()`, состояние одиночки останется.

```python
def test_first():
    auditor = AuditorSingleton.get_instance()
    auditor.record_notification(...)  # Добавили запись

def test_second():
    auditor = AuditorSingleton.get_instance()
    records = auditor.get_records()  # На одну запись больше, чем ожидаем!
```

В нашем проекте это демонстрируется в `TestAuditorWithSingleton::test_auditor_state_leak_between_tests`.

### 2.3 Сложность подмены в тестах

**Проблема:** чтобы подменить конфигурацию, нужно либо:
- Создавать временные файлы,
- Напрямую обращаться к `_instance` (нарушение инкапсуляции),
- Писать хаки для сброса состояния.

```python
# Уродливо: прямой доступ к приватному полю
ConfigurationSingleton._instance = ConfigurationSingleton({...})

# Или: полагаться на файлы
config = ConfigurationSingleton.get_instance("test_config.yaml")
```

В нашем проекте это показано в `TestConfigurationSubstitution`.

### 2.4 Проблемы параллельного выполнения

**Проблема:** если тесты выполняются параллельно (например, в pytest с опцией `xdist`), общее состояние одиночки может вызвать race condition.

Даже если инициализация потокобезопасна, *использование* состояния может не быть. Например:

```python
# Поток 1
config = ConfigurationSingleton.get_instance()
provider = config.get('notification_provider')

# Поток 2 (параллельно)
ConfigurationSingleton.reset()
config2 = ConfigurationSingleton.get_instance("other_config.yaml")

# Поток 1 может получить разные данные между get_instance и get!
```

## 3. Почему альтернатива через внедрение зависимостей предпочтительнее

### 3.1 Явные зависимости

**Решение:** каждый компонент явно указывает, что ему нужно:

```python
class NotificationService:
    def __init__(self, config: Configuration, auditor: Auditor):
        self._config = config
        self._auditor = auditor
```

**Преимущество:** читая сигнатуру, сразу видно, какие компоненты нужны. IDE может подсказать зависимости.

### 3.2 Полная изоляция тестов

**Решение:** каждый тест создаёт свои экземпляры:

```python
def test_one():
    config = Configuration({...})
    auditor = Auditor()
    service = NotificationService(config, auditor)
    # ...

def test_two():
    config = Configuration({...})  # Совсем другой экземпляр
    auditor = Auditor()             # Совсем другой экземпляр
    # Ничего не утекло из test_one
```

**Преимущество:** тесты полностью независимы, нет `reset()`, нет хаков.

### 3.3 Тривиальная подмена зависимостей

**Решение:** просто передать другой объект в конструктор:

```python
def test_with_test_config():
    test_config = Configuration({'notification_provider': 'mock'})
    auditor = Auditor()
    service = NotificationService(test_config, auditor)
    # service будет использовать test_config
```

**Преимущество:** нет хаков, нет обращения к приватным полям, полная прозрачность.

### 3.4 Единственность на приложение без глобального доступа

**Решение:** контейнер управляет жизненным циклом:

```python
container = DIContainer()
config = Configuration.load_from_file('config.yaml')
auditor = Auditor()
service = NotificationService(config, auditor)

container.register_singleton('config', config)
container.register_singleton('auditor', auditor)
container.register_singleton('service', service)

# Во всём приложении есть ровно один экземпляр config
# Но доступ к нему *явный* через контейнер, не через статический метод
```

**Преимущество:** компонент является "единственным" на приложение (потому что контейнер это гарантирует), но не глобальным. Легко заменить на другой контейнер или компоновку в тестах.

## 4. Различие в тестировании

### Вариант одиночки: требуется механизм сброса

```python
def setup_method(self):
    ConfigurationSingleton.reset()  # Обязательный хак
    AuditorSingleton.reset()        # Обязательный хак

def test_something():
    config = ConfigurationSingleton.get_instance()
    # ...
```

**Стоимость:** каждый тест вынужден участвовать в "уборке" глобального состояния. Код смешивает тест-логику с управлением жизненным циклом.

### Вариант внедрения зависимостей: естественная изоляция

```python
def test_something():
    config = Configuration({...})  # Новый экземпляр, готово
    auditor = Auditor()            # Новый экземпляр, готово
    service = NotificationService(config, auditor)
    # ...

def test_something_else():
    config = Configuration({...})  # Другой экземпляр, утечки исключены
    # ...
```

**Стоимость:** ноль. Природная изоляция на уровне самого языка.

## 5. Рекомендации для проекта "Обращения студентов"

| Компонент | Рекомендация | Причина |
|-----------|-------------|---------|
| **Конфигурация** | Внедрение зависимостей | Это просто данные, нужна подменяемость в тестах |
| **Аудит** | Внедрение зависимостей | Это хранилище, которое должно быть заменяемым (файл/БД) |
| **Логирование** | Возможно одиночка | Это действительно ресурс, требующий синхронизации |
| **Подключение к БД** | Одиночка или пул | Это уникальный ресурс, нужна одна точка синхронизации |

## 6. Заключение

**Одиночка — это анти-паттерн для бизнес-компонентов.**

Используйте внедрение зависимостей с управлением жизненным циклом в контейнере:
- Тесты становятся независимыми и простыми
- Архитектура остаётся тестируемой при расширении проекта
- Явные зависимости делают код понятнее
- Подмена реализаций становится тривиальной

**Одиночка оправдан только для инфраструктуры** (БД, логирование, сеть), где действительно нужно одно и то же состояние и требуется синхронизация доступа.
